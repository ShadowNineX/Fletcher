# Doom engine port checklist

The target is the single-player campaign engine in id Software’s GPL Linux Doom 1.10 release, running through Fletcher’s Logic Arrows backend. Use synthetic records and original test maps for parity. Keep the user’s WAD and game assets external. [Pinned upstream source](https://github.com/id-Software/DOOM/tree/a77dfb96cb91780ca334d0d4cfd86957558007e0/linuxdoom-1.10) · [Upstream subsystem inventory](https://github.com/id-Software/DOOM/blob/master/linuxdoom-1.10/FILES)

Read effective neighbor lighting when the line triggers. |

`node tests/doom-native-wall-phase.mjs --bench` builds two muted maps. Open each map at Unlimited speed, enable Key mode, and press **B** to start the timer. The optional `--packets <file>` supplies 2,048 pairs of signed 32-bit texture phases and steps as JSON.

In windowed Logic Arrows, the two maps matched all 2,048 recorded row transitions from a 160×120 E1M1 replay. The physical circuit ran in 147 and 152 ms over 2,086 host ticks. The script ran in 77 and 68 ms over 2,048 ticks with an identical idle circuit on the board. The arrow timing includes writes to 52 input pads per sample and reads from seven outputs. Each lane can accept one sample per tick after the 38-tick circuit delay. The campaign keeps the increment beside the script-owned texture state so the current row can use its result immediately.

A separate per-view slope cache followed `R_ExecuteSetViewSize` by calculating the row factors when the view changed. Two alternating 160×120 E1M1 simulator pairs matched 116 sampled frames, 116 register snapshots after normalizing the derived table and interface tags, and 942,244 display writes in each run. The cache removed 14,156 work checkpoints and median controller CPU fell from 1,410 to 1,398 ms. In windowed Logic Arrows at full detail, Unlimited speed, and zoom 2, 120 frames took 8,243 ms with per-row arithmetic and 8,271 ms with the cache (14.6 and 14.5 FPS). Both ran for 120 host ticks with zero notes. The campaign retains the existing row projection.

The optional `--arrow-colormap` build generates a physical COLORMAP board from the supplied WAD. Blue Arrows and Blue L-Splitters store and scan the 8,704 palette indices in 64 banks. A Script Block captures the aligned arrow outputs once, and the renderer uses the resulting table while drawing the 3D view. The original WAD path supplies the table while the board starts or if a different lump is mounted. The compiler uses ordinary placements and shared bytes. The supplied WAD produced a 13,654,970-byte expanded Level with 429,148 tiles at 320×200.

The initial matched trial used the physical table for walls and planes, with the same board present in both maps. It reproduced every COLORMAP byte, 40 sampled E1M1 frames, and 1,213,621 wall updates. Controller CPU was 1,512 ms with WAD reads and 1,468 ms with the table from arrows in one simulator pair. Disconnecting bit 6 in each bank changed the expected bytes and the visible E1M1 framebuffer. The build option also uses the table for sprites and the weapon view. Compared with the standard build without the board, it matched 32 turning frames and 771,887 wall updates, with 1,011 and 1,142 ms of controller CPU in one simulator pair. The playable arrow map opened E1M1, moved, and fired in windowed Logic Arrows. The desktop FPS gain remains unverified.
